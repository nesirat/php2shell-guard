# Advisory 2026-10-21 — PHP2Shell

**Veröffentlicht:** 2026-10-21
**CVEs:** CVE-2026-109618, CVE-2026-109619
**Kritikalität:** CVSS v4 9.2 (beide)
**Betroffen:** alle PHP-Versionen 5.4 bis 8.5.11, die Web-Requests verarbeiten
**Gepatcht:** 8.5.12, 8.4.27, 8.3.36, 8.2.35 (EOL-Branches: kein Upstream-Fix)

---

## Kurzfassung

Zwei unabhängige Wege zu **unauthentifiziertem Remote Code Execution** in der
PHP-Kern-Logik. Beide sind **nicht** anwendungsabhängig ausnutzbar: der Angriff
trifft die Request-Verarbeitung, bevor Anwendungscode entscheidet.

| CVE | Kette |
|---|---|
| CVE-2026-109618 | Speichererschöpfung → `longjmp()` auf teilweise initialisiertem Request-Speicher → Shutdown verarbeitet ungültigen Zustand → RCE |
| CVE-2026-109619 | Request-State überlebt den Worker → Folge-Request konsumiert freigegebenen Speicher → RCE |

Die Angriffsvektoren sind Multipart-/Upload-Requests mit ungewöhnlich vielen
Teilen, vielen Headern pro Teil, tief verschachtelten Feldnamen sowie
Chunked-Requests ohne verwertbares `Content-Length`. Für CVE-2026-109619 kommt
der `session.upload_progress`-Pfad hinzu (Feldname `PHP_SESSION_UPLOAD_PROGRESS`
in POST-Body bei aktiver Session).

---

## Betroffene Konfigurationen

| Deployment | Risiko | Begründung |
|---|---|---|
| Apache `mod_php` | **kritisch** | mod_php führt den Request-Shutdown auch bei fehlgeschlagenem Startup aus → Angriff ohne Anwendungsbeteiligung |
| PHP-FPM | hoch | bei Startup-Fehler wird der Child beendet; der Zustand kann aber **nach** dem Startup publiziert werden und wird vom nächsten Request konsumiert |
| FrankenPHP | hoch | mod_php-Modell (unkonditionierter Shutdown) |
| LSAPI | mittel–hoch | FPM-Modell |
| php-cgi | mittel | begrenzte Kontrolle über den Worker-Lebenszyklus |
| CLI | gering | kein HTTP-Vektor |

## Mitigation (vorläufig)

Siehe [`MITIGATION.md`](MITIGATION.md) für die vollständige Begründung.

Kurzfassung:

1. `memory_limit = -1` **admin-gesichert** (`php_admin_value` bzw.
   `php_admin_value[]` im FPM-Pool)
2. `session.upload_progress.enabled = 0` **admin-gesichert** (php.ini / Pool / Server-Config)
3. `fatal_error_backtraces = 0` (nur PHP 8.5)
4. `post_max_size` / `upload_max_filesize` klein, `max_input_nesting_level` /
   `max_input_vars` / `max_file_uploads` begrenzen
5. Request-Limits auf Webserver-Ebene (`LimitRequestBody`, `LimitRequestFields`,
   `LimitRequestFieldSize` bzw. `client_max_body_size`)
6. **Alle Worker neu starten**
7. Verfügbarkeitsgrenze per cgroup (`MemoryMax`), **kein** `RLIMIT_AS`/`RLIMIT_DATA`

> **Nur das Update auf eine gepatchte Version behebt die Lücke.**

---

## Detection

Siehe [`DETECTION.md`](DETECTION.md).

Verhaltensindikatoren im Access-Log:

* Requests mit `PHP_SESSION_UPLOAD_PROGRESS` im Body bei gleichzeitiger Session
* ungewöhnlich viele Multipart-Teile pro Request
* viele Header pro Multipart-Teil
* tiefe Verschachtelung der Feldnamen
* Requests ohne `Content-Length` (chunked) mit auffällig großer dekodierter Body-Größe
